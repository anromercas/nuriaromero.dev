- **SEO-17 follow-up (2026-09-22):** a `review-reliability` pass on that first commit found a critical gap: this site has `<ViewTransitions />` enabled site-wide (`src/layouts/Layout.astro`), and Astro does not re-run inline scripts that are byte-identical across pages (as `WhatsAppButton.astro`'s script is, being a shared component) on client-side navigation — only `astro:page-load`/`astro:after-swap` listeners re-run logic per navigation. Fix: extracted the guard into a named function (`initWhatsAppFloatingButtonHeroGuard`) that disconnects any previous `IntersectionObserver` (stored in a module-scoped `whatsAppHeroGuardObserver` variable that survives across un-re-run scripts) before creating a new one, and re-queries the DOM + re-creates the observer on `astro:page-load` — confirmed via `node_modules/astro/dist/transitions/router.js` that this event fires both on the initial hard load (`addEventListener("load", onPageLoad)`) and after every subsequent swap (`onPageLoad()` called after `runScripts()` inside `transition()`), so a single listener now covers both cases (matching `AnalyticsConsent.astro`'s exact pattern). `astro:after-swap` (used by `ThemeToggle.astro`) was considered but rejected: that event exists specifically for paint-critical work that must run before the swapped content is painted (dark-mode class, scroll reset) — this guard isn't paint-critical (the reviewer's fail-safe note already covers a brief visible-button moment), so `page-load`'s slightly later, single-path timing is the better fit and avoids duplicating logic across two lifecycle events.
